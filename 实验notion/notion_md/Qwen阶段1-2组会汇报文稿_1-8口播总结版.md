# Qwen 阶段1-2组会汇报文稿：1-8 口播总结版

更新时间：2026-07-03

## 1. 实验整体设计

我这次汇报的是 Paper 1 目前在 Qwen2.5-7B-Instruct 上的阶段1和阶段2实验结果。

这部分实验主要围绕两个问题：

第一，Rogue 这类 activation steering attack 在真实生成过程中，到底作用在 prefill、decode，还是受到 `use_cache` 影响，并没有真正作用到 generated tokens。

第二，如果我们修正实验，让 steering 真正作用到 generated tokens 后，ASR 下降了，这到底说明模型更安全，还是说明模型输出已经崩坏。

实验设计上，我用了两套维度。

第一套是 A-F 六种 phase/cache 设置：


| 编号  | 方法            | 设置                                           |
| --- | ------------- | -------------------------------------------- |
| A   | `rogue_v1`    | Rogue v1 原始 cache semantics，`use_cache=True` |
| B   | `no_cache`    | `use_cache=False`，每步全序列 forward steering     |
| C   | `decode_only` | `use_cache=True`，只攻击 generated tokens        |
| D   | `full`        | prefill + decode 都 steering                  |
| E   | `first_k`     | first-k decode steering，当前前 3 个 decode token |
| F   | `decay`       | decode decay steering，当前 decay=0.85          |


这里有一个需要先说明的点：当前 attack 实验里的 `first_k` 和 `decay` 不是 prefill + decode，而是 decode-side variants，所以它们没有 `rogue_v1` 那种 prefill-dominant steering。

第二套是强度协议：


| Track   | 含义                                |
| ------- | --------------------------------- |
| Track A | fixed-alpha semantic audit        |
| Track B | Rogue-calibrated，`alpha = c * mu` |


目前 Qwen 已经完成：

- 六个 phase/cache track 的 100-sample judge
- `rogue_v1 / decode_only / full` 三组 full1000 judge
- `no_cache / first_k / decay` 的 full1000 judge 正在补
- Llama3.1-8B 跨模型实验已经启动



## 2. Judge 协议

这次我没有直接把 Rogue 原始的二分类 judge 作为主指标，而是用了一个双层评估协议。

主 judge 是四分类：


| label     | 含义                                 |
| --------- | ---------------------------------- |
| `unsafe`  | 连贯且可操作的有害回答                        |
| `refusal` | 明确拒绝或安全重定向                         |
| `safe`    | benign、abstract、irrelevant，但不是明确拒绝 |
| `broken`  | 空、截断、复读、乱码、语义崩溃                    |


同时我保留 Rogue-compatible 二分类，也就是 `safe / unsafe`。这个指标主要用于和 Rogue 原始实验对齐。

但主结论不能只用 Rogue-compatible ASR，因为 Rogue-compatible 会把很多 short、incoherent、repetitive 输出算作 safe，这会掩盖 collapse。

所以现在的评估分成两层：

第一层是 safety outcome labels，也就是 `unsafe / refusal / safe / broken`。

第二层是 abnormal-generation descriptors，比如 repetition、empty/truncated、garbled、language switch、special-token leakage。

这里要强调：bad case 不是第五个安全类别，也不等于 broken。它是横向异常生成特征，可以和 unsafe、refusal、safe、broken 任意标签共存。

## 4. 阶段1：Phase-Call 机制审计

阶段1回答的是一个机制问题：

> steering 到底实际发生在哪个阶段？

阶段1最关键的证据是 phase-call 审计表。ASR 和 broken 更适合放到阶段2，用来解释不同阶段语义带来的行为后果。

这里我用 Track B 的代表性强度 `c=1.0`，跨 1000 个 random vectors 聚合，得到下面这张 phase-call 语义审计表。

在解释结果前，我先说明一下表头含义。


| 列名                      | 含义                                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------------------- |
| `prefill attack`        | prefill 阶段是否会施加 attack vector                                                                               |
| `decode cached/run`     | 每次 run 平均发生多少次 cached decode forward，也就是 `use_cache=True` 下每步只输入一个新 token 的 decode每次生成里，普通缓存式 decode 跑了多少步 |
| `decode full/run`       | 每次 run 平均发生多少次 full-sequence decode forward，主要对应 `use_cache=False` 时每步重新跑整段序列每次生成里，完整序列重跑式 decode 跑了多少步    |
| `generated steered/run` | 每次 run 平均有多少个 decode step 真正对 generated token 施加了 steering每次生成里，真正被 steering 干预的新生成 token 有多少个             |
| `解释`                    | 根据 phase-call 统计得到的语义判断                                                                                     |



| method        | prefill attack | decode cached/run | decode full/run | generated steered/run | 解释                                                      |
| ------------- | -------------- | ----------------- | --------------- | --------------------- | ------------------------------------------------------- |
| `rogue_v1`    | True           | 70.8              | 0.0             | 0.0                   | prefill-dominant，cached decode 不 steer generated tokens |
| `no_cache`    | True           | 0.0               | 154.2           | 154.2                 | 每步全序列 forward                                           |
| `decode_only` | False          | 189.0             | 0.0             | 189.0                 | 真正 cached decode generated-token steering               |
| `first_k`     | False          | 95.1              | 0.0             | 3.0                   | 只 steer 前 3 个 decode step                               |
| `decay`       | False          | 91.5              | 0.0             | 91.5                  | decode steering，强度衰减                                    |
| `full`        | True           | 159.4             | 0.0             | 159.4                 | prefill + cached decode 都 steer                         |


接下来我按 method 解释这张表。

首先看 `rogue_v1`。

`rogue_v1` 的 `prefill attack=True`，说明它确实在 prefill 阶段施加了 attack vector。同时它的 `decode cached/run=70.8`，说明生成过程中确实发生了 cached decode forward。

但是关键是最后一列：`generated steered/run=0.0`。

这说明虽然模型进入了 decode 阶段，但在 `use_cache=True` 的 cached decode 中，Rogue v1 并没有真正把 steering 施加到 generated tokens 上。因此我们说它是 prefill-dominant，而不是严格意义上的 generation-time steering。

再看 `decode_only`。

`decode_only` 的 `prefill attack=False`，说明它不在 prefill 阶段攻击。它的 `decode cached/run=189.0`，说明它在 `use_cache=True` 条件下走的是 cached decode。最关键的是，`generated steered/run=189.0`。

这说明 cached decode 的每一步 generated token 都被 steering 作用到了。所以 `decode_only` 才是真正意义上的 cached decode generated-token steering。

再看 `full`。

`full` 的 `prefill attack=True`，同时 `generated steered/run=159.4`。这说明它既在 prefill 阶段施加 steering，也在 cached decode 阶段对 generated tokens 施加 steering。

所以 `full` 是 prefill + decode 双阶段 steering。

再看 `no_cache`。

`no_cache` 的 `decode cached/run=0.0`，但 `decode full/run=154.2`，说明它不是 cached decode 单 token 语义，而是在 `use_cache=False` 下，每一步重新跑 full sequence。

同时它的 `generated steered/run=154.2`，说明这些 full-sequence decode step 里 generated positions 被反复 steering。因此 `no_cache` 和 `decode_only` 都会作用到 generated tokens，但语义不同：

- `decode_only` 是 cached decode，每步只处理当前 token；
- `no_cache` 是 full-sequence decode，每步重新处理整段序列。

最后看 `first_k` 和 `decay`。

`first_k` 的 `prefill attack=False`，说明它没有 prefill attack。它的 `generated steered/run=3.0`，正好对应当前设置的前 3 个 decode step。所以 `first_k` 实现的是“只攻击最早几个 generated tokens”。

`decay` 的 `prefill attack=False`，`generated steered/run=91.5`，说明它会持续作用于 decode 阶段，但 steering 强度会按 `decode_decay=0.85` 逐步衰减。

因此，`first_k` 和 `decay` 没有复现 `rogue_v1` 的 ASR 峰值是合理的，因为它们没有 `rogue_v1` 的 prefill attack，而只是 decode-side variants。

所以这张表支撑阶段1的几个机制结论。

第一，`rogue_v1` 在 `use_cache=True` 下不是严格的 generation-time steering，而是更接近 prefill-dominant steering。证据是它 `prefill attack=True`，但 `generated steered/run=0.0`。

第二，`decode_only / full / no_cache` 才是真正会作用到 generated tokens 的设置。证据是它们的 `generated steered/run` 都明显大于 0。

第三，`no_cache` 和 cached decode 的语义不同。证据是 `no_cache` 的 `decode full/run=154.2`，而其他 `use_cache=True` 方法的 `decode full/run=0.0`。

第四，`first_k / decay` 是 decode-side variants，不是 prefill + decode。证据是它们的 `prefill attack=False`。

因此阶段1的机制结论是：

> 同样叫 activation steering，实际发生在 prefill、cached decode，还是 no-cache full decode，会产生完全不同的实验语义。Rogue v1 under `use_cache=True` 更接近 prefill-dominant steering，而不是严格的 generated-token steering。



## 5. 阶段2：Decode Collapse 诊断

阶段2回答的是：当 ASR 下降时，模型是真的更安全，还是输出崩坏了。

这个问题很重要。因为如果只看 ASR，我们可能会把模型崩坏误解为攻击失败，甚至误解为安全增强。

Track A fixed-alpha 基本稳定，没有明显 ASR、broken 或 ARR 异常。因此阶段2重点看 Track B Rogue-calibrated。

100-sample 六组结果如下：


| method        | peak ASR       | max broken     | max ARR        | 诊断                      |
| ------------- | -------------- | -------------- | -------------- | ----------------------- |
| `rogue_v1`    | 20.0% @ c=1.50 | 20.0% @ c=2.00 | 23.0% @ c=2.00 | 有攻击峰值，collapse 可控       |
| `no_cache`    | 11.0% @ c=1.25 | 97.0% @ c=2.00 | 84.0% @ c=2.00 | 高强度 collapse            |
| `decode_only` | 5.0% @ c=1.25  | 98.0% @ c=2.00 | 92.0% @ c=2.00 | 典型 decode-time collapse |
| `first_k`     | 0.0%           | 0.0%           | 1.0%           | 稳定，但没有攻击成功              |
| `decay`       | 0.0%           | 0.0%           | 2.0%           | 稳定，但没有攻击成功              |
| `full`        | 9.0% @ c=1.00  | 97.0% @ c=2.00 | 84.0% @ c=2.00 | 强 collapse              |


这里最重要的现象是：`decode_only / full / no_cache` 在高强度下 broken 接近 97-98%，但它们的 ASR 反而低于 `rogue_v1`。

所以低 ASR 不能直接解释为安全拒绝增强。更合理的解释是，模型输出已经进入 collapse。

## 6. Full1000 稳健性验证和 Bad-Case 证据

目前 full1000 已完成三组：

- `rogue_v1`
- `decode_only`
- `full`

结果如下：


| method        | peak ASR       | max broken     | max ARR        | max repetition |
| ------------- | -------------- | -------------- | -------------- | -------------- |
| `rogue_v1`    | 19.4% @ c=1.50 | 16.8% @ c=2.00 | 22.8% @ c=2.00 | 7.1% @ c=2.00  |
| `decode_only` | 3.7% @ c=1.25  | 97.1% @ c=2.00 | 87.3% @ c=2.00 | 65.3% @ c=2.00 |
| `full`        | 6.8% @ c=1.00  | 96.9% @ c=2.00 | 86.1% @ c=2.00 | 58.1% @ c=2.00 |


full1000 验证了 100-sample 的趋势。

`rogue_v1` 在 c=1.50 附近形成稳定 ASR 峰值，大约 19-20%。但 `decode_only` 和 `full` 虽然 ASR 低很多，broken 却接近 97%，repetition 也很高。

这说明 generated-token steering 的强度升高后，模型主要进入 collapse，而不是稳定越狱。

bad case 方面，100-sample 六组结果是：


| type                 | count |
| -------------------- | ----- |
| repetition           | 817   |
| empty_or_truncated   | 136   |
| language_switch_like | 78    |
| garbled              | 16    |


full1000 前三组结果是：


| type                  | count |
| --------------------- | ----- |
| repetition            | 5779  |
| empty_or_truncated    | 910   |
| language_switch_like  | 635   |
| garbled               | 75    |
| special_token_leakage | 2     |


这里再次强调：bad case 不等于 broken。

bad case 是横向异常生成特征。它可以和任意 judge label 共存。比如 bad case + unsafe，说明文本虽然异常，但可能仍然包含有害信息；bad case + refusal，说明模型拒绝了，但输出形式异常；bad case + broken 才是典型 collapse。

所以 bad-case 统计不是替代四分类 judge，而是解释输出到底如何异常。

## 7. 当前结论

目前 Qwen 的阶段1和阶段2支持几个判断。

第一，phase/cache semantics 会显著影响 activation steering 的实际含义。

第二，公开 Rogue v1 在 `use_cache=True` 下更接近 prefill-dominant steering，而不是真正稳定的 generation-time steering。

第三，真正 generated-token steering，尤其是 `decode_only / full / no_cache`，在高强度下主要导致 collapse。

第四，ASR 下降不能直接解释为攻击变弱或模型更安全，必须结合 broken、ARR、repetition、empty/truncated 等指标判断。

第五，Rogue-compatible ASR 只能作为对齐指标，不应作为论文主结论指标。
